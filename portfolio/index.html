01

Problem
Definition

흩어진 정보와 서로 다른 기준 때문에 초보 캠퍼는 자신에게 맞는 장소를 비교하고 예약 전 확인까지 이어가기 어렵습니다.

가설

정보 파편화

지도, 블로그, 예약처를 반복해서 오갑니다.

가설

조건 이해 부족

숙박 유형과 필요한 시설을 판단하기 어렵습니다.

가설

비교 기억 부담

여러 탭의 정보를 사용자가 직접 기억해야 합니다.

확인된 한계

재고 오해

공공데이터는 실시간 재고와 최종 요금을 보장하지 않습니다.

02

Data
Insight

저장소와 구현에서 확인된 사실과 추가 검증이 필요한 사용자 가설을 분리했습니다. 출처가 확인되지 않은 숫자는 성과로 사용하지 않습니다.

KNOWN EVIDENCE

저장소에서 확인된 구현 근거

검색·필터·최대 3곳 비교·공공데이터·예약 준비 기능이 실제 코드에 존재합니다.

03

Pain Points
& HMW

문제를 기능 이름이 아니라 사용자의 행동과 판단 부담으로 정리했습니다.

정보의 파편화

후보마다 다른 정보 형식 때문에 다시 정리해야 합니다.

번거로운 예약 여정

날짜와 조건을 반복 입력하고 실제 예약처를 다시 찾아야 합니다.

리뷰 신뢰도 부족

작성 맥락과 호스트 답변을 구분하기 어렵습니다.

호스트 도구의 부재

예약·문의·후기·정산 확인이 분산됩니다.

HOW MIGHT WE
어떻게 하면 초보자가 필요한 조건을 쉽게 이해하고, 후보를 같은 기준으로 비교하며, 데이터의 한계를 인지한 채 다음 예약 행동으로 이동하게 할 수 있을까?

Trade-offs &
Limitations

구현 완료, 연결 구조, 프로토타입을 구분해 실제 결과와 설명의 신뢰도를 맞춥니다.

공공데이터 API 의존

실시간 재고·요금 부재 가능 → 출처와 재확인 안내

정적 사이트의 CSR·SEO 한계

핵심 상세 사전 렌더링과 서버 검증이 다음 단계

결제·호스트 인증 미완성

실제 권한·정산·감사 로그는 운영 백엔드 필요

“어디까지 사용했고 어디부터 실제 백엔드 구축이 외부 모듈 연동이 필요한지, 그 명확한 한계를 스스로 이해하고 있는 설계자임을 보여드립니다.”
